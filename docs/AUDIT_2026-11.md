# System audit and rebuild, November 2026

This report records what was wrong with the question-answering path, what was
changed across the codebase, how the result was measured, and what remains
limited. The current design is described in [ARCHITECTURE.md](ARCHITECTURE.md).

## Follow-up verification on 24 November 2026

The starting commit, `11a1a2e`, passed 575 offline tests. It already assigned
distinct evidence IDs to the parts of a split provision. Applying the three
handoff patches together reproduced the reported failure in
`test_model_judged_gaps_and_clarifications_are_passed_through`. The service
had cleared the citations for an insufficient answer but kept their numbers.
The response builder now removes the model's markers before returning that
status. The original regression test passes.

The final offline suite passed 708 tests with five skips. Four tests require
an explicit database URL, and one OCR test requires local Tesseract English
data. `ruff check .` passed.

### Findings and fixes

| Area | Trigger and correction |
|---|---|
| Provider failures | A refusal by one Gemini model could end the race while another could still answer. A refusal leaves the other model eligible, including with retries and hedging disabled. Credential rejection stops the exchange. Pending calls are drained and the parallel limit is three. |
| Rate limits | An earlier call finishing late could erase a stated wait. The scheduler preserves the wait across late results, grants at most one post-wait retry per model per exchange, and reports the provider's original wait to the caller. The local cooldown cap is 900 seconds. |
| Request budget | Question restatement, answer generation, correction and OpenAI failover now use the remaining request time. Restatement is capped at six seconds by default. A named-provision request that runs out of time can return cited statute text. |
| Citation placement | A marker after a full stop, consecutive markers, a numbered list or an abbreviation could attach a quote to the wrong sentence. Placement now uses statement boundaries, preserves indentation and statute brackets, and uses numbers or position to link translated text. Every returned citation has a marker. Fallback windows end on a word boundary. |
| Catalogue and follow-ups | Asking what a named Act covers had produced the catalogue. The catalogue requires a question about the collection. A remembered law now breaks close ranking ties. An independent new topic such as “and receipts?” can switch laws even in a short follow-up. |
| Law names and bare sections | A title sharing words with a different published law could lose a distinctive qualifier. Explicit titles now retain it. Recent unknown titles end stale law context. Bare section-plus-topic searches compare the requested sections across laws and ask for clarification when no candidate stands out. |
| Named-law topic searches | The title itself could supply the only keyword hit and suppress better evidence elsewhere. The search separates the subject from the title and reports when the better matching passage belongs to another law. |
| Schedules and cross-references | A bare schedule now includes numbered schedules. Schedule 1 can resolve to a single unnumbered schedule. Reference expansion checks the target kind and the neighbouring instrument name, including citations to a parent Act within rules. |
| Evidence size and exact limits | A long split schedule used to exhaust the prompt. The best matching part and its neighbours are selected within both budgets. Exact searches honour the caller's passage limit and still identify missing provisions. During a model outage the response copies the full published display text of each selected passage and names any missing requests. |
| Spelling and extracted text | Spelling repair made substitutions such as “wedding” to “bedding” and scanned the vocabulary for every unknown word. Only eight words per query receive a lookup, with tighter rules for short words. Display cleanup removes identifiable footnotes fused to words and citation years. The source text and its offsets remain available for quote verification. |
| Publication cache | Truncated metadata, a damaged vector file or a failed write could prevent a restart. Cache reads validate a vector checksum and discard damaged pairs. Both files are synced before publication, temporary files are cleaned up, and only the current and previous cache generations are retained. |
| Publication refresh | Cached data could survive loss of approval or vector coverage. Cold and cached loads and background refreshes verify approved pins, hashes and row counts. Empty or failed loads are throttled. Snapshot construction and cache I/O run off the event loop. Cold loads stream the large tables, with embeddings transferred in pgvector's binary format. |
| Query cost | Repeated year scans in acronym matching added work for every word. One scan per question suffices. Three 4,000-character samples covering ordinary English, Urdu and provision lists completed in 13–96 ms on the in-memory fixture. |
| API and platform | The rate limiter now uses the ASGI client address. Streamed bodies receive the same 413 as an oversized declared body. API keys are compared as bytes, request IDs are allowlisted, and access logs use matched route templates. The development administration gate checks the peer, Host and browser origin. Cancellation coverage checks both the question slot and inference queue. |

### Live publication and generation

The server loaded both local models and served the active Supabase publication
`legalmind-pilot-20261016` with question recording disabled. Database checks
used read-only queries. The publication contains 23 laws, 531 chunks and 2,815
provision nodes. The cold-load queries returned 2,473 page mappings. Requests
for Section 3 with both “Punjab” and “Punjb” returned HTTP 200 with status
`partial` during a Gemini outage. A separate SQL read matched both quotes to
the active published chunk and verified the provision, source span, file hash
and PDF page 4 (the one-based `page_index`). A retrieval-only check on the final code found that
section for both spellings again. Given a previous question about gambling,
“section 19 about receipts?” switched to Section 19 of the Consumer Protection
Act in the same publication.

Earlier cold reads lost a database connection during vector transfer. With
streamed binary vectors, two independent cold loads took 590 and 407 seconds
on this connection. A verified cache reload took 17 seconds and reproduced the
chunk text, source spans, vectors and cross-reference maps. A fresh connection
for the final repository test exceeded its original 30-second limit. The
integration harness now has a separate, configurable connection budget and
retry count. A direct check retrieved the same provision by label and by
reference path, including four source references. The complete PostgreSQL
suite subsequently passed all four tests in 12 minutes 11 seconds against the
same Supabase publication. Its two cold loads took 302 and 332 seconds and
the verified cache load took 7.6 seconds.

The evaluation made one pass over all 52 cases with a five-second pause
between questions. Nine passed. Nineteen cases required `answered` and
received `partial`, and 24 received `service_unavailable`. All 20 text-only
replies, including the one accepted as a pass, cited a provision in the
corresponding expected set. One generated legal answer passed. The other
successful cases were handled without generation. Gemini returned 429 and
503 during the run. Median latency for `answered` and `partial` replies was
13.93 seconds, with a 90th percentile of 25.01 seconds. The provider-dependent
52-of-52 target remains unverified on this host. The evaluation was not
repeated after additional follow-up routing and database transfer fixes.

OpenAI failover was covered with a test client. A live OpenAI credential was
unavailable in the project configuration. Credential rotation remains an
operator action in the owning provider projects.

## The reported problem

> "What is Section 3 of Punjab Prevention of Gambling Ordinance 1978?" is
> answered. "What is Section 3 of Punjb Prevention of Gambling Ordinance 1978?"
> is not.

The second question failed in 0.0 seconds with `insufficient_evidence` and no
model call. It was one instance of a general weakness: the pipeline refused
questions instead of trying to understand them.

## How the system was examined

The whole repository was read first. The previous pipeline was then run
unchanged on a database built from the 23 pilot PDFs through the project's own
ingestion code (same counts as the shared database: 23 laws, 2,815 provisions,
531 chunks), with the real embedding model and the real answer model. Fourteen
questions of the kinds users ask were recorded, with the SQL statements and
model calls each one made.

| Question | Before | After |
|---|---|---|
| Section 3 of **Punjab** Prevention of Gambling Ordinance 1978 | answered, 6.6 s | answered, 1.5 to 2 s |
| Section 3 of **Punjb** Prevention of Gambling Ordinance 1978 | `insufficient_evidence` | answered |
| Section 3 of the **Prison** Act 1894 (title says "Prisons") | `insufficient_evidence` | answered |
| "**sction** 5 of the ... Ordinance" | answered, 15.4 s, 4 model calls | answered, 1 call |
| "sections 3 **to** 5 of the ..." | `clarification_needed` | answered, all three sections |
| "section 3 gambling law punjab" | `clarification_needed` | answered |

Of twelve answerable questions the previous pipeline answered four.

## Root causes

**A. Law names had to be spelt exactly.** `explicit_law_mentions` and
`resolve_laws(explicit=True)` required every word of a title to match. Spelling
repair used a fixed list of about ninety words. A name that did not resolve
ended the request as "no results". This is the reported failure, and the same
code rejected "Prison Act" for "The Prisons Act".

**B. Unreadable references were refusals.** Ranges, spelt-out numbers,
misspelt keywords and a section number without a law each led to a
clarification request or a refusal instead of a search.

**C. Citation checking was all or nothing.** A quote had to match the stored
text character for character, including PDF line breaks and footnote digits
such as `1[three years]`. One imperfect quote discarded the entire answer
("I can't verify a source-backed answer"), after 10 seconds of work.

**D. Provider errors were final.** One 503 or timeout from the answer model
became `service_unavailable`.

**E. The request path was slow by construction.**

- 19 to 28 SQL statements per question. Against the shared database each round
  trip costs about a second from the team's location (the earlier speed notes
  measured `SELECT 1` at 0.96 to 1.74 s with 0.02 ms of server time), so
  retrieval and context expansion alone took 40 to 100 seconds.
- A large cross-encoder reranker ran on every question on CPU: 4 to 10 seconds
  on the test host for a small ranking gain.
- Two to four model calls per question (generation, analysis review,
  repairs), and a further one for conversation routing when history was sent.
- The inference runtime admitted two jobs and rejected the rest.

**F. Operational defects.** A fresh install could not start (FlagEmbedding is
incompatible with current transformers). Uploading a PDF with a source URL
raised `NameError`. A second, older extraction stack wrote rows the current
pipeline cannot read. The structure parser opened a false "Schedule" when a
sentence wrapped just before that word, swallowing the sections after it.

**G. Related provisions were invisible.** A penalty clause that says
"contravenes sections 18 to 22" shares no words with a question about receipts
(section 19), so "what if they refuse?" could not find it.

## What changed

### Query understanding and retrieval (`app/retrieval`)

- The active publication is held in memory as an immutable snapshot, loaded
  with plain `SELECT`s, cached on disk and refreshed in the background.
  Answering a question now runs **no SQL**. No migration is needed.
- Law names are resolved by weighted word matching with stems and bounded edit
  distance. Nothing is hard-coded per law.
- References are parsed tolerantly: abbreviations, misspelt keywords, spelt
  numbers, lists, ranges, mixed lists and ranges, nested addresses, schedules.
- Keyword search (BM25) repairs misspelt query words against the collection's
  own vocabulary; dense search uses the published vectors; the two are fused.
- A follow-up inherits the law and wording it needs from the conversation.
- The snapshot indexes which provisions cite which by number, in both
  directions.

### Answering (`app/qa`)

- One structured model call per question (two when a poorly matched question
  is first restated).
- Reranking is budgeted: it runs only where the hardware can afford it.
- Evidence contains whole provisions plus definitions, referenced provisions
  and the provisions that cite them.
- Citations are verified quote by quote with tolerant matching; a bad quote is
  dropped, not the answer. Named-but-uncited provisions are linked.
- The model client works inside one deadline with retries, racing calls, a
  fallback model, overload cool-down, rate-limit handling and optional OpenAI
  failover. Without any model, named provisions are still quoted.

### Platform

- One validated settings class; request middleware with request ids, size
  limits and security headers; optional API keys; rate limiting; admission
  control; liveness and readiness probes; structured logs that never contain
  questions, prompts or credentials.
- Local administration routes exist only in development and only for loopback
  callers, checked before the body is read.
- Database TLS can verify the server certificate (`DB_SSL_ROOT_CERT`).

### Ingestion and indexing (Phase A and B)

- Structure parser v13: a wrapped "Schedule", "rule" or "article" no longer
  opens a provision. All 23 stored revisions re-parse identically.
- Workers: configurable lease, job released on shutdown, backoff on transient
  errors, parsing moved off the event loop.
- A page whose table detection failed goes to review instead of passing
  silently. Upload failures return clear 422/503 responses.
- Contract uploads store a sanitised file name; an abandoned extraction can be
  reclaimed; extraction refuses a stored path outside the upload directory.

### Removed, after checking that nothing used it

- The previous Phase C implementation (`app/services/qa`, `legal_query`,
  `legal_retrieval`, `retrieval_fusion`, `model_runtime`, three repositories,
  the split QA configuration and five schema modules) and its tests.
- The older extraction stack (`legal_extraction_worker`, `legal_pdf_extraction`,
  `pdf_process` and its repository). The inspector's page preview was kept as
  `legal_preview.py`.
- Nineteen duplicate or one-off scripts; the rest are grouped under
  `scripts/pipeline`, `scripts/audit` and `scripts/eval` and run as modules.
- `FlagEmbedding` (replaced by `transformers`, already a dependency) and
  `docling` from the server requirements (now `requirements-contracts.txt`).
- Four unused definitions found by a reference search across both branches.

### Deliberately left alone

- The database schema and every migration.
- The `/ask` and `/search/legal` response fields.
- The location of Phase A and B modules, which other branches are still
  changing; moving them would only create merge conflicts.
- `contract_citations.py` and the first-generation `build_chunks`, which are
  exercised by tests and belong to unfinished contract work.
- The evidence gate, by request.

Other checks:

- **Concurrency.** Twelve simultaneous questions: all answered, median 2.4 s,
  slowest 8.7 s. Twenty-four simultaneous questions exceeded the API key's
  per-minute quota: 13 answered and 11 returned 503 (8 from the server's own
  queue limit, 3 from the provider).
- **Consistency.** Four questions asked three times each cited the same
  provisions every time.
- **Pipeline replay.** A fresh database was migrated and filled from the 23
  PDFs with the current code (register, extract, structure, approve, chunk,
  embed, publish). The published chunk text is identical, law by law, to the
  collection built before the changes.
- **Schema compatibility.** The snapshot loader's five queries were run against
  a database migrated only to `20261016_17`, the revision recorded for the
  shared database. Answering questions needs no newer migration.
- **Existing configuration.** An `.env` in the team's current format (spaces
  and quotes around values, retired variables) loads unchanged.
- **Container.** The included `Dockerfile` was built with
  `DOWNLOAD_MODELS=false` and run with the model cache mounted. The container
  ran as a non-root user, passed its health check, answered the misspelt
  question above in 1.9 s, and returned 404 for `/docs` and the administration
  routes in production mode. The image's own model-download step was not
  exercised in that build; the same command was run directly on the host.

## Limits that code cannot remove

1. **The answer model's availability and quota.** With the supplied key,
   `gemini-3.5-flash-lite` starts returning 429 at roughly twenty calls a
   minute, with stated waits of 15 to 34 seconds, and it has a daily request
   cap that one day of testing (several hundred questions) used up. Under
   sustained load some questions take 10 to 20 seconds or fail, and once the
   daily cap is reached only the fallback model answers. On the day of testing the
   other models the key can call (`gemini-3.1-flash-lite`, `gemini-3.5-flash`,
   `gemini-3.8-flash`) were returning 503 for minutes at a time, and
   `gemini-flash-lite-latest` is the same model as the primary, so a different
   Gemini fallback would not have helped. A higher quota, or an
   `OPENAI_API_KEY` for failover to a second provider, is the remedy.
2. **Distance to the database** no longer affects questions, but it still
   affects start-up (one snapshot load, then cached) and the ingestion tools.
3. **Reranking on CPU** is skipped by default because it costs more than the
   rest of the request. A GPU host can turn it on.
4. **The OpenAI path** is covered by unit tests with a fake client only; it was
   not exercised against the live service.
5. **The evaluation is a regression check, not legal review.** It verifies that
   the right provision is cited with an acceptable status. Whether an
   explanation is legally sound still needs a person.
6. **Rate limiting and model cool-downs are per process.** Several processes
   each keep their own counters.
7. **Local administration has no login.** It is confined to development and
   loopback; exposing it would need authentication first.

## Open observations

Noted during the audit and not changed, because they concern local
administration paths and need the owners' judgement:

- When a revision has several source files, the persisted audit
  (`LegalStructureRepository.audit`) derives its page and table findings from
  the primary source only; the approval check's page list covers every source.
  No revision in the pilot collection has more than one source, so nothing is
  affected today.
- Some audit and validation work runs on the event loop inside administration
  requests, and the publication routes load the tokenizer in the request.
- Upload and OCR data directories are resolved relative to the working
  directory; a deployment should set absolute paths.
